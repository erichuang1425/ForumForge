# Project health and impact

This ledger separates implementation activity from real open-source adoption.
Update it monthly from public, source-linked evidence. Use zero or “not measured”
instead of estimates.

## Monthly update template

### YYYY-MM

- **Releases:** version and release link, or none.
- **Adoption:** store active installs/downloads and methodology, or not measured.
- **Usefulness:** supported engines/sites and a link to compatibility evidence.
- **Maintenance:** issues triaged/closed, PRs reviewed/merged, and median initial
  response where GitHub provides enough data.
- **Community:** first-time contributors, external fixtures/adapters, pilot
  feedback, and public acknowledgements.
- **Reliability/security:** regressions, compatibility refreshes, advisories, and
  time to remediation.
- **Next action:** one measurable project-health objective for the next month.

## Evidence rules

- Link GitHub releases, issues, PRs, compatibility records, or store dashboards.
- Distinguish author/maintainer work from independent community contribution.
- Do not count generated issues, commits, tests, or lines of code as adoption.
- Do not publish private user data or private vulnerability details.
- Correct prior entries visibly if a metric or attribution was wrong.
